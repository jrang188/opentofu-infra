# terraform/hermes/

## Responsibility

Second live OpenTofu root module: provisions one small standalone
Hetzner Cloud VM that hosts the "hermes agent" — an always-on LLM
coding-agent daemon — and enrols it in the Tailnet. It owns the VM,
the firewall, the SSH key registration, and the tailnet identity, and
nothing else: the agent install itself is deliberately deferred to a
manual step outside Terraform (see README "Hermes VM"). No Kubernetes
provider, no cluster resources, no shared state with `terraform/k3s/`.

## Design

A single flat root — no modules, no `kube-hetzner` wrapper — split by
concern:

- `hermes.tf` — the resources. `hcloud_firewall.hermes` has an empty
  `rule` list on purpose: Hetzner Cloud firewalls are default-deny
  allowlists, so zero rules means no public inbound on any port, the
  same policy as the cluster's `firewall_ssh_source = null`. Egress is
  not filtered by hcloud firewalls. `hcloud_ssh_key.hermes` registers
  the operator's public key as a backup path; primary access is
  Tailscale SSH. `hcloud_server.hermes` is `cx22` / `ubuntu-24.04` /
  `fsn1` by default, labelled `provisioner=terraform,role=hermes`, and
  carries a cloud-init `user_data` that installs `tailscale` from apt
  and runs `tailscale up --ssh --accept-dns=true` with the auth key,
  hostname, and `tag:hermes`. `--accept-dns=true` is safe here — unlike
  the k3s nodes, this VM has no etcd peer-TLS constraint forcing
  MagicDNS off. The firewall is attached via `firewall_ids` on the
  server, not via `hcloud_firewall_attachment` (both target the same
  server field; using both would double-attach). No
  `delete_protection` / `prevent_destroy`: nothing external points at
  the VM yet, and its MagicDNS identity is regenerated by cloud-init on
  recreate. No `hcloud_network` — a tailnet-only standalone VM does not
  need a private net, and adding one later forces a rebuild.
- `onepassword.tf` — secret sourcing, same pattern as
  `terraform/k3s/onepassword.tf`. Only the hcloud token is an
  `ephemeral` resource (provider auth — never in state). The SSH public
  key and the Tailscale auth key are plain `onepassword_item` data
  sources because `hcloud_server.user_data` cannot take ephemeral
  values: the auth key lands in state in plaintext, the same exposure
  the k3s root accepts. The key item is `tailscale-auth-key-hermes`
  (new, tagged `tag:hermes`) rather than the k3s root's
  `tailscale-auth-key` (bound to `tag:k8s-control-plane`): auth-key
  tags are fixed at creation, so reusing it would enrol this VM under
  the wrong ACL identity. Manual prerequisite: create the key tagged
  `tag:hermes` and add `tag:hermes` to `tagOwners` in the Tailnet ACL.
- `terraform.tf` — `required_version = "~> 1.12"`; providers `hcloud
  ~> 1.62` (major pin, blocks a silent 2.x bump — AGENTS.md hard rule)
  and `onepassword 3.3.1` (pinned exactly, matching k3s). No
  `kubernetes` provider, so this root never needs a kubeconfig and can
  be applied independently of the cluster. Committed lockfile is its
  own.
- `providers.tf` — `hcloud` token from
  `ephemeral.onepassword_item.hcloud_token.credential`; `onepassword`
  pinned to the same account UUID as the k3s root, authenticating via
  the `op` CLI session.
- `variables.tf` — `hermes_server_name` (regex-validated DNS label,
  doubles as the Tailscale hostname), `hermes_server_type` (default
  `cx22`; bump to `cx32`/`cx42` for RAM if the agent needs it),
  `hermes_location` (default `fsn1`, same as the cluster),
  `hermes_image` (default `ubuntu-24.04`), `hermes_tailscale_tag`
  (regex-validated `tag:*`, default `tag:hermes`), and
  `tailscale_magicdns_domain` (regex-validated `*.ts.net`, no default).
  All `nullable = false`.
- `outputs.tf` — `server_id`, `ipv4_address` (public but
  firewall-blocked; informational), and `tailscale_hostname`
  (`<name>.<magicdns domain>`, the only address worth using). No
  tailscale-IP output: the 100.x address is assigned by Tailscale at
  boot and never known to Terraform.
- `terraform.tfvars.example` — copy to `terraform.tfvars` (gitignored).
  Holds only non-secret sizing/domain values; secrets come from
  1Password via the provider.

## Flow

1. Manual prerequisites: the 1Password item `tailscale-auth-key-hermes`
   (reusable, non-ephemeral key tagged `tag:hermes`), `tag:hermes` in
   the Tailnet ACL `tagOwners`, and an `op` CLI session on the applying
   machine.
2. `cd terraform/hermes && cp terraform.tfvars.example
   terraform.tfvars`, fill in `tailscale_magicdns_domain`.
3. `tofu init` — independent of `terraform/k3s/`; own state, own
   lockfile.
4. `tofu plan -out=hermes.tfplan` — review. The auth key showing in
   `user_data` is expected.
5. `tofu apply hermes.tfplan` — server boots and enrols in the tailnet
   via cloud-init. Verify with `tailscale status` on the operator
   machine.
6. `ssh <hermes_server_name>.<tailscale_magicdns_domain>` — Tailscale
   SSH, no host-key juggling and no public port.
7. Agent install: out of scope here. Read the README "Hermes VM"
   section.

Teardown is `tofu destroy` from the same directory. Nothing in the
cluster references this VM, so order against `terraform/k3s/` does not
matter.

## Integration

- Consumes: the Hetzner Cloud API (token from 1Password), the Tailnet
  (auth key tagged `tag:hermes`), and the 1Password SSH key item. No
  dependency on the k3s root, its snapshot, or its state.
- Consumed by: the operator on a Tailnet-joined host with an `op`
  session; the (future, manually installed) hermes agent daemon on the
  VM itself.
- Cross-repo: the `tag:hermes` ACL identity and `tagOwners` entry live
  in the Tailnet policy, not in this repo — see
  `docs/homelab-ecosystem.md` for the tag conventions shared with
  `homelab-nix` and `homelab-k8s`.
- State is local and unencrypted and contains the Tailscale auth key
  (via `user_data`) and the kube-adjacent nothing else — enable
  `TF_ENCRYPTION` before the first apply on a new machine, same rule as
  the cluster root.
